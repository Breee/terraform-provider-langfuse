# Generating the Langfuse Terraform provider from OpenAPI

Research date: 2026-09-11

## Recommendation

Use **Speakeasy for a parallel proof of concept**, not as an in-place rewrite of
the current provider. Speakeasy is the better of the two requested options for
this API because its Terraform target is GA and models Terraform lifecycle
semantics explicitly. OpenAPI Generator's `terraform-provider` target is
experimental and relies mainly on REST conventions and tags.

Do not replace the current provider until generated resources pass state and
behavior compatibility tests. The published Langfuse specification is not a
complete description of the existing provider:

- It has no `/api/admin/organizations` operations. Therefore it cannot generate
  the existing `langfuse_organization` or `langfuse_organization_api_key`
  resources.
- Projects have create, update, and delete operations, but no get-by-ID
  operation. The current provider reads all projects and selects one by ID.
- Membership creation is a workflow: organization membership may first create
  a SCIM user, then update a membership. This is not a conventional CRUD path.
- Project and organization membership endpoints use `PUT` as an idempotent
  create/update operation and identify a member in the request body.
- Project API keys can be listed but not fetched individually. Their secret is
  returned only at creation and must be retained in Terraform state.
- LLM connections use an upsert operation and a list operation rather than
  separate create, read-by-ID, and update operations.
- Existing resources carry credentials in resource state and use custom import
  IDs. A generated provider will naturally prefer provider-level authentication
  and may generate different import formats.

The safe target architecture is initially hybrid: retain hand-written resources
whose lifecycle is not represented by the specification, and evaluate generated
resources one at a time. Speakeasy supports registering additional custom
resources through `terraform.additionalResources`; an alternative is to keep
the generated provider separate until migration is proven.

## Input assessment

Specification:
<https://cloud.langfuse.com/generated/api/openapi.yml>

Observed properties:

| Property | Finding | Consequence |
| --- | --- | --- |
| OpenAPI version | 3.0.1 | Supported by both tools. |
| Terraform annotations | No `x-speakeasy-*` or `x-terraform-*` annotations | A separate overlay is required. |
| Authentication | HTTP Basic | Supported by both, but it represents project or organization keys, not the admin key used by two existing resources. |
| Organization admin API | Absent | Organization and organization API-key resources cannot be generated from this spec. |
| Project API | Create/list/update/delete; no get-by-ID | Drift detection and import need list filtering or custom code. |
| Membership API | List/update/delete; no conventional create | Needs explicit idempotent/multi-step lifecycle mapping. |
| Project API keys | Create/list/delete; secret only returned on create | Needs state preservation and list filtering. |
| LLM connections | List/upsert/delete | Needs idempotent create/update mapping and list filtering. |

Keep the downloaded upstream specification immutable. Store Terraform-specific
meaning in an
[OpenAPI Overlay](https://spec.openapis.org/overlay/latest.html), because the
URL is generated by Langfuse and local edits would be lost.

## Comparison

| Criterion | Speakeasy | OpenAPI Generator |
| --- | --- | --- |
| Terraform target maturity | GA, support level 2 | Experimental |
| Generated implementation | Plugin Framework provider, API client, CRUD connectors, docs | Plugin Framework provider, simple client, resource/data source templates |
| Resource mapping | Explicit `x-speakeasy-entity` and `x-speakeasy-entity-operation` lifecycle mapping | One resource and one data source per tag; CRUD auto-detection or undocumented `x-terraform-is-*` overrides |
| Nonstandard lifecycle support | Multiple calls per lifecycle operation, idempotent create/update, polling, transforms, custom resources | One selected create/read/update/delete/list operation per tag |
| Schema composition | Documents `oneOf`, `anyOf`, and `allOf` handling | Declares `oneOf`, `anyOf`, and `allOf` unsupported |
| Authentication | Global Basic, Bearer, API key, OAuth client credentials, and custom schemes | Basic, Bearer, and API key; generated provider exposes generic auth fields |
| Drift and missing objects | Generated read connectors; HTTP 404 removes state; configurable missing codes | Generated read path, based on one operation selected for the tag |
| Imports | Generated for resources with a viable read mapping | Generated ID passthrough based on the selected read path parameter |
| Validation and plans | Generated validators and plan modifiers; custom extensions available | Required/optional/computed inference; limited customization through templates/extensions |
| Documentation | Uses `terraform-plugin-docs`; examples and import docs | Generates a README and provider example; generator currently declares no API/model doc templates |
| Regeneration | Managed workflow (`speakeasy run`), overlays, hosted workspace/API key | Local deterministic CLI; pin the image/JAR version and commit config/templates |
| Testing | Tests must still be authored; Speakeasy states automated Terraform tests are not yet generated | Generated make target exists, but meaningful Langfuse acceptance coverage must be authored |
| Licensing/operation | Commercial platform and authenticated CLI | Apache-2.0 open source; local Java/npm/Docker execution |
| Fit for this repository | Better lifecycle model and hybrid extension points | High customization burden due to shared tags and non-CRUD API shapes |

### Why Speakeasy is preferred

Speakeasy treats Terraform resources as entities with lifecycle operations,
rather than assuming each API tag is one resource. Relevant capabilities for
Langfuse include:

- `Entity#create,update` for idempotent upsert endpoints.
- Ordered operations such as `Entity#create#1` and `Entity#create#2` for a
  multi-call workflow.
- Separate resource and data-source read associations.
- `x-speakeasy-match` for path/body identifiers with different names.
- API response transforms and entity hoisting for wrapped list responses.
- `x-speakeasy-terraform-ignore` and custom Terraform types for fields that do
  not map cleanly.
- Additional hand-written resources and dependencies in `gen.yaml`.

This does not make the conversion automatic. The generated result still needs
explicit compatibility work for current resource schemas, sensitive values,
imports, write-only values, and missing-object behavior.

### Why OpenAPI Generator is higher risk

As of OpenAPI Generator 7.25.0, `terraform-provider` is experimental. The
implementation groups operations by OpenAPI tag, then chooses at most one
create, read, update, delete, and list operation for each tag. It can infer
common REST patterns or use these vendor extensions:

- `x-terraform-is-create`
- `x-terraform-is-read`
- `x-terraform-is-update`
- `x-terraform-is-delete`
- `x-terraform-is-list`
- `x-terraform-exclude`
- `x-terraform-resource-name`
- `x-terraform-sensitive` on properties

Those extensions are visible in the generator implementation but are not in
its public generator option table. Treat them as unstable. Langfuse also puts
organization memberships, project memberships, organization projects, and
organization API keys under the `organizations` tag. The overlay would have to
retag operations into one tag per Terraform entity before generation.

## Procedure A: Speakeasy

### 1. Work in an isolated branch and output directory

Do not point a first generation at the repository root. Generated files can
replace `go.mod`, `README.md`, provider code, examples, and documentation.

```bash
git switch -c spike/speakeasy-provider
mkdir -p .work/speakeasy
curl -fsSL \
  https://cloud.langfuse.com/generated/api/openapi.yml \
  -o .work/speakeasy/langfuse.openapi.yml
```

Record a checksum so that upstream changes are reviewable:

```bash
sha256sum .work/speakeasy/langfuse.openapi.yml
```

### 2. Install and authenticate the CLI

Use the current official installer after reviewing it, or download a release
binary from the Speakeasy CLI releases page.

```bash
curl -fsSL https://go.speakeasy.com/cli-install.sh | sh
speakeasy auth login
```

For CI, create a workspace API key and provide it as `SPEAKEASY_API_KEY`. Do not
commit the key.

### 3. Validate the source

```bash
speakeasy lint openapi --non-interactive \
  -s .work/speakeasy/langfuse.openapi.yml
```

Review errors and warnings before adding Terraform mappings. In particular,
inspect request/response mismatches, unconstrained objects, nullable fields,
and create responses that do not contain identifiers.

### 4. Create a Terraform overlay

Create `.work/speakeasy/terraform-overlay.yml`. Start with one low-risk entity,
not every public endpoint. The following illustrates the required concepts for
the project resource; JSONPath targets and component names must be checked
against the downloaded revision before use.

```yaml
overlay: 1.0.0
info:
  title: Langfuse Terraform mappings
  version: 0.1.0
actions:
  - target: $.paths["/api/public/projects"].post
    update:
      x-speakeasy-entity-operation: Project#create
  - target: $.paths["/api/public/projects/{projectId}"].put
    update:
      x-speakeasy-entity-operation: Project#update
  - target: $.paths["/api/public/projects/{projectId}"].delete
    update:
      x-speakeasy-entity-operation: Project#delete
  - target: $.components.schemas.Project
    update:
      x-speakeasy-entity: Project
```

Do not mark the project list operation as `Project#read` until the proof of
concept demonstrates deterministic filtering by the current resource ID.
Without that, refresh and import are not correct.

Likely mappings to investigate next:

| Existing resource | Candidate mapping | Required special handling |
| --- | --- | --- |
| `langfuse_project` | POST create, PUT update, DELETE delete, list-based read | Select project by ID; preserve `retention_days`; preserve current credentials and four-part import format or migrate state. |
| `langfuse_project_api_key` | POST create, list-based read, DELETE delete | Immutable fields; preserve one-time secret and public key in state; identify key in list. |
| `langfuse_project_membership` | PUT `create,update`, GET list/read, DELETE | Match member identity carried in request body; preserve composite identity/import behavior. |
| `langfuse_organization_membership` | Ordered SCIM create plus membership update, GET list/read, DELETE | Existing conditional SCIM workflow may require a custom resource rather than generated calls. |
| `langfuse_llm_connection` | PUT `create,update`, GET list/read, DELETE | Filter paginated list by ID and preserve project credentials and secret fields. |
| `langfuse_organization` | Not available | Keep hand-written until an admin OpenAPI spec exists. |
| `langfuse_organization_api_key` | Not available | Keep hand-written until an admin OpenAPI spec exists. |

For upsert endpoints, the eventual annotation can use this form:

```yaml
x-speakeasy-entity-operation: LlmConnection#create,update
```

Use `x-speakeasy-match: id` on a differently named path/body parameter when
needed. Use an ordered operation only when the operation is unconditional;
the current organization-membership SCIM call is conditional, so a custom
resource is likely safer.

Validate and apply the overlay into a disposable artifact:

```bash
speakeasy overlay validate \
  -o .work/speakeasy/terraform-overlay.yml
speakeasy overlay apply \
  -s .work/speakeasy/langfuse.openapi.yml \
  -o .work/speakeasy/terraform-overlay.yml \
  --out .work/speakeasy/langfuse.terraform.openapi.yml
```

### 5. Generate outside the current provider

The interactive path is the documented primary workflow:

```bash
speakeasy quickstart
```

From the repository root, choose
`.work/speakeasy/langfuse.terraform.openapi.yml`, select `terraform`, use
provider name `Langfuse` and package name `langfuse`, and select
`.work/speakeasy/generated-provider` as the output directory.

The equivalent non-interactive initialization is:

```bash
speakeasy quickstart --skip-interactive --output console \
  -s .work/speakeasy/langfuse.terraform.openapi.yml \
  -t terraform \
  -n Langfuse \
  -p langfuse \
  -o .work/speakeasy/generated-provider
```

Quickstart creates `.speakeasy/workflow.yaml` and generation configuration.
For ongoing use, configure the remote source plus local overlay so each run
fetches the current upstream contract:

```yaml
workflowVersion: 1.0.0
speakeasyVersion: latest
sources:
  langfuse:
    inputs:
      - location: https://cloud.langfuse.com/generated/api/openapi.yml
    overlays:
      - location: terraform-overlay.yml
    output: langfuse.terraform.openapi.yml
targets:
  langfuse-provider:
    target: terraform
    source: langfuse
    output: generated-provider
```

After the proof of concept, pin the Speakeasy version accepted by the team
instead of retaining `latest`.

Relevant `gen.yaml` settings are:

```yaml
terraform:
  version: 0.1.0
  author: langfuse
  packageName: langfuse
  forwardCompatibleEnumsByDefault: true
  additionalDependencies:
    github.com/hashicorp/terraform-plugin-testing: v1.13.3
  additionalResources: []
```

Use `additionalResources` for hand-written resources only after proving that
their package can be maintained outside generated files.

Regenerate with:

```bash
speakeasy run --output console
```

### 6. Evaluate before integration

Build and test generated code in the repository's Docker test sandbox. Do not
rely only on successful generation.

The proof of concept passes only if all of the following hold:

1. The generated resource address remains `langfuse_<existing_name>`.
2. Every existing attribute keeps its name, type, required/optional/computed
   mode, sensitivity, replacement behavior, and null/unknown semantics.
3. Refresh detects remote drift and removes state only for a confirmed missing
   object.
4. Import works without putting secrets on a command line where avoidable.
5. One-time API-key and connection secrets survive refresh.
6. Existing Terraform state produces an empty plan after switching binaries.
7. Unit and Docker-backed acceptance tests cover create, refresh, update,
   import, drift, and delete.

Integrate one resource at a time. Keep generated code and custom code in
separate packages, and never hand-edit files marked as generated.

## Procedure B: OpenAPI Generator

This procedure is suitable for an experiment, not a production migration at
the current generator maturity.

### 1. Pin the generator and prepare isolated input/output

The official Docker image avoids a host Java installation. Pin the version;
the current documented stable version on the research date is 7.25.0.

```bash
git switch -c spike/openapi-generator-provider
mkdir -p .work/openapi-generator/input .work/openapi-generator/output
curl -fsSL \
  https://cloud.langfuse.com/generated/api/openapi.yml \
  -o .work/openapi-generator/input/langfuse.openapi.yml

docker run --rm \
  -v "$PWD/.work/openapi-generator:/local" \
  openapitools/openapi-generator-cli:v7.25.0 validate \
  -i /local/input/langfuse.openapi.yml --recommend
```

### 2. Create a generator-specific overlay

Do not feed the unmodified spec directly to this target. First create an
overlay that:

1. Removes unrelated API operations with `x-terraform-exclude: true`.
2. Replaces shared Langfuse tags with exactly one tag per Terraform entity.
3. Marks one operation per lifecycle role with `x-terraform-is-create`,
   `x-terraform-is-read`, `x-terraform-is-update`,
   `x-terraform-is-delete`, or `x-terraform-is-list`.
4. Sets `x-terraform-resource-name` to the exact existing resource suffix.
5. Marks secret schema properties with `x-terraform-sensitive: true`.

Illustrative operation after applying such an overlay:

```yaml
/api/public/projects:
  post:
    tags: [project]
    x-terraform-resource-name: project
    x-terraform-is-create: true
```

For `/api/public/projects/{projectId}`, mark update and delete explicitly. There
is no suitable read-by-ID operation in the source specification. Generating a
resource without a correct read operation is not acceptable for production.

Apply the overlay with an OpenAPI Overlay tool and save the result as
`.work/openapi-generator/input/langfuse.terraform.openapi.yml`. Speakeasy's
overlay subcommands can perform this preprocessing even when OpenAPI Generator
is the code generator, or another standards-compliant overlay tool can be used.

### 3. Generate

```bash
docker run --rm \
  -v "$PWD/.work/openapi-generator:/local" \
  openapitools/openapi-generator-cli:v7.25.0 generate \
  -g terraform-provider \
  -i /local/input/langfuse.terraform.openapi.yml \
  -o /local/output \
  --git-host github.com \
  --git-user-id langfuse \
  --git-repo-id terraform-provider-langfuse \
  --additional-properties=providerName=langfuse,providerAddress=registry.terraform.io/langfuse/langfuse,providerVersion=0.1.0,packageName=provider,hideGenerationTimestamp=true
```

Inspect supported options for the pinned version rather than assuming options
from a newer release:

```bash
docker run --rm openapitools/openapi-generator-cli:v7.25.0 \
  config-help -g terraform-provider
```

Never generate directly over the repository. The target emits `main.go`,
`go.mod`, `README.md`, `.gitignore`, a makefile, provider/client packages, and
examples.

### 4. Evaluate generated behavior

Apply the same compatibility gates listed for Speakeasy. In addition, inspect:

- Whether each generated tag produced exactly one intended resource and data
  source.
- Whether the chosen read operation and path parameter generated a valid ID and
  import implementation.
- Whether Basic authentication maps correctly to Langfuse public/secret keys.
- Whether nested objects and lists retain values rather than falling back to
  strings.
- Whether API errors, 404 handling, pagination, and one-time secrets are safe.
- Whether regeneration with the same pinned image is deterministic.

Expect custom templates or hand-written code for Langfuse's list-based reads,
upserts, membership workflow, and existing state schema. Maintaining a template
fork is effectively maintaining a generator and should be counted in the cost
comparison.

## Migration plan for this repository

1. **Freeze the contract.** Capture the live spec and checksum in a proof-of-
   concept branch. Inventory current schemas and import formats from tests.
2. **Start with one resource.** `langfuse_project` is understandable but exposes
   the missing get-by-ID issue. `langfuse_llm_connection` tests upsert and
   pagination. Either is a useful discriminator.
3. **Generate in parallel.** Keep output under `.work/` or a separate repository.
   Do not overwrite the current `provider/` or `langfuse/` packages.
4. **Close lifecycle gaps.** Prefer overlays and supported extension points.
   Keep conditional workflows or unavailable endpoints hand-written.
5. **Prove state compatibility.** Create state with the released provider,
   switch to the candidate binary, refresh, and require an empty plan. Exercise
   import and remote deletion.
6. **Adopt incrementally.** Register one proven generated resource while the
   remaining resources stay hand-written. A full generated replacement is not
   justified until the admin API is represented and every lifecycle is tested.
7. **Pin and automate.** Pin generator versions, review upstream spec diffs,
   regenerate in CI, and reject uncommitted generated diffs.

## Decision gate

Choose Speakeasy if the proof of concept can preserve the public Terraform
schema while using overlays and a small, explicit custom-code layer. Its
lifecycle mapping and composite-schema support make that outcome plausible.

Choose OpenAPI Generator only if avoiding a managed/commercial generator is a
hard requirement and the team accepts ownership of custom preprocessing and
templates. Its current direct Terraform target is not a lower-maintenance path
for this Langfuse API.

Keep the current hand-written provider if either proof of concept changes state
semantics, loses secrets, cannot implement reliable reads, or requires forking
most generated lifecycle code. OpenAPI can still generate only the Go API
client while the existing Plugin Framework resources remain hand-written; that
is a smaller and more controllable automation boundary.
